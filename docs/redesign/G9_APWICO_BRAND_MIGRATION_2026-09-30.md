## Implemented repository migration

- Public and private UI, public tools/resources/templates/occupation/region/comparison
  pages, methodology, pricing/trust/legal surfaces, extension UI, generated emails,
  document filenames, metadata, schema and social assets now identify APWICO.
- Canonical origin, sitemap and robots references are `https://apwico.com`; route paths are
  preserved one-for-one. `www.apwico.com`, `resumestride.com` and
  `www.resumestride.com` have a 301 implementation that is disabled by default behind
  `BRAND_DOMAIN_REDIRECTS_ENABLED=false`.
- The redirect preserves the full path and query and normalizes `/index.html` to `/`. It
  does not activate merely because code is deployed, preventing premature production
  cutover and redirect loops.
- The extension defaults to APWICO but temporarily accepts the exact legacy HTTPS root.
  Look-alike hosts, credentials, paths, queries, fragments and alternate ports remain
  rejected. The unpublished store status remains unchanged.
- New document clients read `X-APWICO-Qualified-Conversion`; the server also emits the old
  header for shipped-client compatibility. The old local billing test header remains a
  fallback only and is never trusted in hosted Vercel environments.
- `npm run brand:check` rejects the old public name/support address/canonical outside the
  explicit compatibility boundary and reports the retained-reference count.

## State and ownership safety

These values deliberately remain unchanged: `resumestride.resume.v1`, its rescue key,
`resumestride.jobDraft`, onboarding continuation keys, locale choice, first-touch
attribution, extension message types, Stripe owner/catalog metadata and Stripe lookup
keys. Their preservation is tested. Database projects, tables, owner IDs, entitlement
records, payment/customer/subscription references and migration history are not recreated
or renamed.

Cloud data remains owner-scoped because the Supabase project and user/database identities
do not change. Account switching and authorization rules remain the existing tested
boundary. A new browser origin cannot read the old origin's local/session storage. This is
a browser security rule, not something a redirect can solve safely. Therefore:

1. Keep the redirect gate off during the dual-domain rehearsal.
2. Keep the old origin available long enough for users to sign in/sync or download any
   browser-only resume and job-specific work.
3. Publish a clear, consent-based transition notice before enabling the redirect; never
   put resume/job content in a URL, analytics event or cross-origin continuation payload.
4. Exercise old-origin local draft, cloud account, recovery, entitlement and cancellation
   scenarios against the release candidate.
5. Enable the redirect only after the owner approves the retention window and the
   production smoke matrix passes. Keep a rollback path to disable the flag immediately.

Because the repository cannot establish the number or recency of browser-only production
drafts, the retention-window decision and live rehearsal remain validation pending; no
“no users” assumption is used to bypass them.

## URL and SEO migration map

- Every existing public `https://resumestride.com/<path>` maps to
  `https://apwico.com/<path>`; private routes retain their path but remain noindex.
- APWICO canonical, Open Graph, Twitter, structured-data and sitemap URLs must be present
  before redirects are activated.
- Add and verify all domain variants in Google Search Console, submit the APWICO sitemap,
  use Change of Address where supported, retain old properties and monitor index/404/
  redirect coverage. No rankings or field traffic are claimed in advance.
- Keep one-hop permanent redirects and do not redirect missing routes to the homepage.
  Keep the old domain and TLS active through the monitoring window.

## External cutover checklist (owner-authenticated; not executed)

1. **Domain/hosting:** verify control of `apwico.com`; attach apex and preferred host to
   the existing Vercel project; preserve mail records; validate TLS and preview build;
   retain the existing project/data rather than recreating it.
2. **Supabase/Auth:** add APWICO Site URL and exact recovery/magic-link callback URLs while
   retaining old callbacks during migration; review email templates/sender links; test
   same-tab and new-tab recovery and both-account isolation.
3. **Email:** verify `apwico.com`/support sender with the existing provider, update SPF,
   DKIM and DMARC without deleting unrelated records, and verify delivery/reply handling
   for `support@apwico.com`.
4. **Stripe:** update public business/product/support branding only after confirming legal
   account identity; verify statement descriptor rules, portal and checkout return URLs,
   webhook endpoint/signature delivery, invoices/receipts, refunds and existing
   subscriptions. Preserve customer/subscription IDs and legacy metadata/lookup keys.
5. **Analytics/search:** rename labels or create the appropriate APWICO property without
   losing historical access; verify privacy-safe events on the new host; configure Search
   Console properties, sitemap and migration monitoring. Do not fabricate a baseline.
6. **Extension:** update listing/site links only after a real store listing/version exists;
   retain exact legacy-host compatibility through the declared migration window. Task 37
   stays blocked until publication facts exist.
7. **Release:** snapshot/recovery check; deploy candidate without redirect; run old/new host
   auth, cloud, billing, export, ownership, local-state and noindex tests; obtain explicit
   owner release approval; then enable DNS/canonical host and finally the redirect flag.

## Rollback

Disable `BRAND_DOMAIN_REDIRECTS_ENABLED`, restore the previous canonical host at the edge
only if required, keep both domains and provider callbacks valid, and do not roll back or
rewrite database/payment identifiers. Investigate with content-free request/account IDs;
never place resume/job text in logs. A rollback does not authorize a production change.
