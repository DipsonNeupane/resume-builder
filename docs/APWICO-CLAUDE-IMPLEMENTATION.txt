Version: October 27, 2026

Apwico is pre-launch and has no existing users. Claude Code will run from a terminal inside the actual Apwico repository. Optimize for a clean launch; do not spend time building customer migrations, legacy subscription compatibility or historical entitlement preservation. Existing code, uncommitted work, secrets and external infrastructure still require care. No existing users does not mean every database or billing resource is disposable. ROLE AND OUTCOME
Act as the engineer implementing these changes inside the existing Apwico repository. Inspect the repository before choosing architecture. Implement working vertical slices, not just a plan or static screens. Preserve useful existing functionality and unrelated work. 8. Commit only if repository policy and user instructions allow it. Otherwise leave clearly scoped diffs. Do not fabricate successful tests or integration results.

B. Extraction correctness
Create a regression fixture with this fictional resume:
Customer support specialist at Example Company, 2022-present. Supported customers across email, phone and live chat. Used Salesforce CRM to resolve billing issues. Trained three new team members. Improved help centre documentation.
Job requirements, first as a paragraph and then as separate bullet lines:
Experience supporting customers across email, phone and live chat. Experience with Zendesk administration. Ability to coach new team members. Workforce scheduling experience. Preferred: Spanish language proficiency.

Test extraction separately from evidence classification.
Handle sentence boundaries, heading scopes, bullet variants, copied text and reasonable deduplication. Preserve source wording and location references. Do not solve this by requiring users to reformat postings or by silently sending private local-tool text to a server.
C. Host and storage checks
Review www versus bare-domain redirect/canonical/indexing behavior. Previously www emitted noindex while the bare domain allowed indexing; do not remove noindex from private workspace routes. Prepare host consolidation through the existing hosting mechanism.
Make draft state accurate: local session, saved locally if persistent, saving to account, saved to account, save failed. Never label a temporary session draft permanently saved.

PHASE 2 — TRACKER AS THE BACKBONE
Implement or simplify a single application record per saved opportunity for a given user. Support jobs found inside Apwico and jobs added externally. Reuse existing IDs and records rather than duplicating user history.

Stages:
saved = interested, application not started
preparing = actively preparing materials
applied = submission confirmed
interviewing = interview process underway
offer = offer received
closed = inactive, with a separate reason

Closed reasons: rejected, withdrawn, role_closed, no_response, archived, other. No response must never automatically mean rejected. Do not infer rejection after an arbitrary delay. Record prior stage and allow correction/reopening.

Model requirements, mapped to existing architecture:
- owner/user ID and access policy
- job/company/title/source URL, source identifiers where available
- posting snapshot, captured/checked timestamps, salary/currency/period when supplied
- stage, closed reason, application/submission date
- next action and due date; optional recruiter/contact and notes
- links to resume versions/documents
- timestamps and an event history sufficient to explain stage changes
- update origin (user, confirmed supported capture, or suggestion)

Do not use title/company alone for hard deduplication. Normalize supported public job identifiers, handle URL tracking parameters carefully, and prompt before merging ambiguous records. Do not strip meaningful identifiers. Different openings at the same company may be legitimate.

Provide:
1. Quick add: company, role and stage first; other fields optional.
2. Paste a public job URL: use the existing supported import mechanism. If fetching fails, retain the URL and allow manual completion. Any server URL fetch must use the repository's SSRF protections and validated public HTTP(S) targets.
3. Search and filters for stage, company, dates and needs-attention.
4. A useful list view as default; board view only if already present or straightforward to reuse.
5. One-click stage updates with appropriate date collection, undo/correction and visible save/error feedback.
6. A job detail record with Overview, Application materials, Timeline and Notes; avoid excessive nested navigation.
7. Spreadsheet import if an importer exists. Otherwise implement a bounded CSV importer with mapping, preview, row errors and duplicate review. Export plain user data in a safe CSV format, escaping spreadsheet formula injection. Do not require an XLSX dependency for the first release.

Schema requirements: one clean launch model using existing useful relationships. No historical user-status backfill or customer migration is required. Update setup/migration scripts so a fresh development database can reproduce the schema and access policies. Seed only explicit development/test fixtures. Do not reset a remote database. All reads/writes must enforce ownership server-side, including documents, events and imports.

DONE: a test user can organize 100 fixture records, find an application, change/reopen its stage, attach a next action and recover a failed save. Another test user cannot access those records. Fresh database setup is reproducible. Fixtures stay in development/test environments.

PHASE 4 — CONNECT EVIDENCE AND TAILORING TO EACH JOB
Primary action on a saved job: Prepare my application.
Flow:
1. Review important extracted requirements. Add/edit/remove items and correct required/preferred classifications, keeping original source text available and distinguishing user edits.
2. Compare with the existing resume. If none exists, offer import or create; do not force rebuilding an existing resume.
3. Clarify missing/related evidence using targeted questions. Let users skip, remain unsure, or confirm absence. Never infer a credential or competence from preference answers.
4. Review suggested changes. Show original wording, proposed wording, supporting user fact and targeted requirement. Accept/reject/edit individually; support undo.
5. Save a separate job-specific version. Preserve the master unchanged. Version metadata records its source revision.
6. Export and apply through the original employer destination.
7. Ask whether the user submitted; only a confirmation or reliable supported submission signal changes the stage to applied.

Use concise labels: Evidence found; Related evidence — review; No evidence found in this resume. Preserve existing distinctions and avoid a dominant candidate/ATS percentage or hiring prediction.
Save clarified facts only with user awareness and appropriate existing storage consent. Reuse approved facts where suitable, preserving context, dates, ownership/contribution scope and edit/delete controls. Build this on existing resume/profile models first; avoid a large new knowledge graph in this release.
Treat postings as untrusted input. AI must not obey instructions embedded in a posting or introduce unsupported tools, metrics, credentials or responsibility. Preserve existing data minimization and consent boundaries. Do not expose private resume content in URLs or telemetry.

Attach the exact submitted/exported version to the application. An immutable content snapshot or existing immutable document version is acceptable. Editing the master later must not change the historical submitted version. Store private artifacts using existing protected storage and access controls. Retain the PDF/DOCX distinction: PDF preserves design; Word may be an editable-content document.

DONE: user can go from saved job to reviewed tailored resume and recorded application; master and historical documents remain unchanged; unsupported suggestions are blocked or explicitly require factual correction; Apply click alone never marks submission.

PHASE 6 — DISCOVER CARDS AND OPTIONAL SWIPING
Use the existing job feed/provider. Implement a list view and a card view with identical underlying results/actions.
Card fields: title, company, location and actual remote restrictions, salary when posted, job type where supplied, source/last checked, 2–3 truthful recommendation reasons, and important uncertainty. Distinguish preference compatibility from resume evidence. Show unknown fields honestly.
Actions: Pass, View details, Save. Visible buttons are mandatory; swiping is optional enhancement. Save does not apply. Support undo and keyboard/screen-reader operation. Do not let horizontal gestures prevent normal vertical scrolling or activate actions accidentally.
Use manageable batches and a clear end state. Do not optimize endless scrolling or raw swipe volume. Passing a job does not permanently exclude a role/company unless the user explicitly chooses that preference. An optional pass reason can improve preferences. Deduplication and closed/stale posting handling must be explicit and use actual provider signals; do not fabricate verification or freshness.

DONE: same actions work without gestures, undo restores state, duplicate saves do not create duplicate records, preference changes update results, and every displayed recommendation reason is supported by available data.
